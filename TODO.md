# Agent capabilities implementation plan

Baseline: `649899d`. Phases 1, 2 and 4 are complete; phase 3 is in progress and phases 5–6 are pending. Verify the referenced files against the current branch before implementation.

## Scope and execution order

Keep OpenCode as Nimbot's sole AI engine. Preserve one container, one persistent workspace, and one FIFO per agent. Keep bot credentials, chat connections, and authorization on the Nimbot Server. Keep model-triggered execution inside agent containers. Use the existing SQLite databases and Docker volumes. For this pre-stable release, update schema initialization directly.

| Phase | Deliverable | Depends on |
| --- | --- | --- |
| 1 | OpenCode tool bridge and task identity | Current task flow |
| 4 | Agent memory | 1 |
| 2 | Advanced approvals and decision history | 1 |
| 3 | Agent communication and delegation | 1, 2 |
| 5 | Shared tools and external MCP integrations | 1, 2 |
| 6 | End-to-end verification and documentation | 1–5 |

Rows are in build order; section numbers below keep their original numbering. Build phase 4 right after phase 1: it needs neither approvals nor Server calls, so phases 1 and 4 form the smallest shippable slice.

The proposed first release covers one-hop asynchronous delegation, private per-agent memory, and panel-managed access to curated external MCP tools. It leaves multi-hop orchestration, shared memory and workspaces, arbitrary MCP stdio commands, OAuth, and a tool marketplace for separate decisions.

### Trust boundary

The Agent Host and OpenCode run as the same user (uid 1000) in one container, and the model has a shell. Anything the Host can read, the model can read: state files, capabilities, and any credential placed in the container. Treat the container as a single untrusted principal.

- Enforce grants, approvals, schemas, and read/write classification on the Nimbot Server. Checks in the Host or the MCP adapter are input hygiene, never the guarantee.
- Keep every credential the model must not use directly on the Server. A capability inside the container may only grant what that agent's current task is already allowed to do.
- Derive no permission, grant, or approval state from data stored in the container.

### Triggered tasks

Tasks started by a schedule or a webhook receive none of the new tools by default. A webhook payload is external data inside the prompt, so delegation and mutating tools on those tasks need a separate, explicit decision.

A definition contains a stable ID, label, approved remote HTTPS endpoint, enabled tools and argument schemas, and an explicit read/write classification per tool. Store per-agent grants separately. Keep credentials scoped to each agent and integration, stored on the Server in a private directory following the `bot-secrets` pattern. They never enter an agent container. The panel can set, replace, or remove a secret without returning its value.
- [ ] Expose a catalog editor, per-agent grant controls, and a bounded connection test in the panel. Run discovery from the Server against an administrator-approved endpoint and display sanitized status and tool names. Discovery cannot execute tools. Treat remote tool metadata as untrusted and require the administrator to confirm the tools and schemas. Use the pinned OpenCode and MCP fixture from phase 1 to validate the integration path. [OpenCode MCP reference](https://opencode.ai/docs/mcp-servers/)
- [ ] Expose only granted catalog entries through the bundled MCP adapter, which forwards each call to the Server. The Server holds the MCP client for remote Streamable HTTP, with per-agent credentials, timeouts, response limits, and redirects disabled. Use a compatible maintained MCP client if the transport needs a library. A credential inside the container could be read by the model and used with `curl`, bypassing approvals and pinned schemas, so remote calls must not run there. The Server only connects to catalog endpoints and passes administrator-pinned tool arguments; it never runs agent-generated commands. Reject model-supplied endpoints. The Server enforces the granted tool ID, pinned schema, and classification before contacting the remote server. Because the Server now makes outbound requests to administrator-entered URLs, restrict catalog endpoints to HTTPS and document that the administrator is trusted to choose them.
- [ ] Treat unknown or changed tools as disabled until reviewed. Apply the advanced approval rules to mutating tools and recheck grant and schema immediately before execution. A remote server's read-only annotation alone cannot qualify a tool for a persistent allow rule. Cancel on turn termination where supported. Persist an invocation intent before a mutating call, record uncertain outcomes, and avoid replaying an uncertain write after a retry or restart.
- [ ] Verify with a local fixture configured only for tests. Grant one definition to two agents with independent credentials, revoke one grant, and show that only the remaining agent can call it. Cover disabled definitions, ungranted tools, schema changes, missing credentials, timeout, redirect rejection, denial before an upstream call, uncertain delivery, and secret redaction. Assert that no credential or upstream URL appears in any container file, environment variable, or tool payload. Use fixture recordings to assert call counts and the identity used for each connection.
