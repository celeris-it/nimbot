# Agent capabilities implementation plan

Baseline: `649899d`. Phase 1 is in progress; phases 2–6 are pending. Verify the referenced files against the current branch before implementation.

## Scope and execution order

Keep OpenCode as Nimbot's sole AI engine. Preserve one container, one persistent workspace, and one FIFO per agent. Keep bot credentials, chat connections, and authorization on the Nimbot Server. Keep model-triggered execution inside agent containers. Use the existing SQLite databases and Docker volumes. For this pre-stable release, update schema initialization directly.

| Phase | Deliverable | Depends on |
| --- | --- | --- |
| 1 | OpenCode tool bridge and task identity | Current task flow |
| 4 | Agent memory | 1 |
| 2 | Advanced approvals and decision history | 1 |
| 3 | Agent communication and delegation | 1, 2 |
| 5 | Shared tools and external MCP integrations | 1, 2 |
| 6 | End-to-end verification and documentation | 1–5 |

Rows are in build order; section numbers below keep their original numbering. Build phase 4 right after phase 1: it needs neither approvals nor Server calls, so phases 1 and 4 form the smallest shippable slice.

The proposed first release covers one-hop asynchronous delegation, private per-agent memory, and panel-managed access to curated external MCP tools. It leaves multi-hop orchestration, shared memory and workspaces, arbitrary MCP stdio commands, OAuth, and a tool marketplace for separate decisions.

### Trust boundary

The Agent Host and OpenCode run as the same user (uid 1000) in one container, and the model has a shell. Anything the Host can read, the model can read: state files, capabilities, and any credential placed in the container. Treat the container as a single untrusted principal.

- Enforce grants, approvals, schemas, and read/write classification on the Nimbot Server. Checks in the Host or the MCP adapter are input hygiene, never the guarantee.
- Keep every credential the model must not use directly on the Server. A capability inside the container may only grant what that agent's current task is already allowed to do.
- Derive no permission, grant, or approval state from data stored in the container.

### Triggered tasks

Tasks started by a schedule or a webhook receive none of the new tools by default. A webhook payload is external data inside the prompt, so delegation and mutating tools on those tasks need a separate, explicit decision.

## 2. Add advanced approvals

The current Host approval event in `apps/agent-host/src/tasks.ts` carries a title and ID. The Server forwards it using `bot-tasks.ts`, with channel-specific pending records in `approvals.ts` and `discord-approvals.ts`. Keep that flow for existing OpenCode permission requests. Use structured, service-validated actions for the new policy rules.

- [ ] Add a Server SQLite store for structured approval requests and decisions. Record the originating agent and task, actor and origin, action type, normalized target, bounded redacted summary, expiry, and outcome. Use atomic transitions for pending, approved, denied, expired, and cancelled requests. Track execution separately so an approval alone cannot be mistaken for a completed action.
- [ ] Add explicit **Ask each time**, **Deny**, and **Always allow** rules in the authenticated panel. Scope every rule to a single agent, capability, and exact target. An explicit deny takes precedence. Default new writes to asking each time, and offer persistent allow only for actions the service can verify as read-only. Show rule expiry and revocation controls. Use trusted operation identifiers for policy evaluation. Keep model text and ACP permission titles out of rule matching.
- [ ] Route confirmation buttons to the initiating task's verified Telegram or Discord conversation. For a delegated child, resolve confirmation to the original conversation through its saved parent link. The callback must verify the current owner and binding, task, deadline, and single-use decision token. Provide authenticated panel history and rule editing. Keep decisions for chat-originated tasks bound to the original owner.
- [ ] Authorize immediately before the side effect. Recheck task state, rule, grant, and action fingerprint. Any change to the approved action requires a new decision. Expiry, failed delivery, task cancellation, or uncertain restart recovery denies unresolved requests. Store terminal outcomes for review and keep interrupted side effects from replaying.
- [ ] Extend `approvals.test.ts`, `discord-approvals.test.ts`, and the panel tests. Verify duplicate and concurrent clicks, stale bindings, revoked rules, changed action arguments, restart, and the two chat channels. Assert that denied or expired requests produce zero side effects.

## 3. Add agent communication and delegation

- [ ] Add directed grants in Server SQLite. In the panel, let the administrator select a source, target, and permission to send a note or delegate a task. Default to no grants and disable self-targeting. Initially allow a grant only when both agents have the same configured Telegram owner ID. For requests originating in Discord, also require matching configured Discord owner IDs. Recheck ownership and the source's verified origin on each request. When ownership or a binding changes, invalidate affected pending requests and grants.
- [ ] Expose four tools through the bridge: list allowed agents, send a note, delegate a task, and read delegation status. Return only granted agent IDs and display names. Represent notes as bounded inbox entries, with a separate tool for the recipient to list its unread notes. Reading or receiving a note must never start a task. Mark content as originating from another agent and treat it as untrusted data.
- [ ] Extend `apps/server/src/task-queue.ts` and `agent-task-services.ts` to admit a durable delegated task with an explicit internal origin carrying the parent task ID and source agent ID. The `tasks` table `CHECK` constraints currently require a Telegram or Discord origin; update them in schema initialization. Keep scheduler and chat origin invariants. Save a pending handoff when the tool call is accepted. In one SQLite transaction, mark the parent completed, recheck the grant, resolve the handoff, and insert the child into the target FIFO. Use a unique source task and invocation ID to deduplicate admission. Kick the target worker only after the transaction commits. Apply existing readiness checks when the target claims the child.
- [ ] Return the delegation ID immediately. Use the existing FIFO on the destination and never wait on a child from the parent's running turn. The child is admitted only when the parent completes, so the status tool reports `pending` for the rest of that turn; say so in the tool description. Status and results are read from a later task of the requesting agent. Reject further delegation from children, cap the number of children per parent, and bound handoff text and result size. Pass only the explicit brief. Run the child in a fresh OpenCode session without replacing the target's saved owner conversation session. Keep both containers and workspaces separate.
- [ ] Persist a bounded child result for retrieval by the requesting agent and send one outcome update to the saved initiating chat after verifying its binding. Reuse the delivery abstraction and delivery-intent handling for uncertain sends. Keep note bodies and results out of logs and unrelated contexts. Show queued, running, completed, failed, cancelled, and interrupted states in the panel. Expose a panel action to cancel the specific child. If the parent fails or is cancelled before handoff, discard the pending delegation and record the reason.
- [ ] In recovery, preserve queued work and completed results. Mark interrupted executions with the existing recovery path and record delegation state without replaying side effects. Deny new admission or result delivery after the corresponding grant or origin is revoked. Handle stopped or deleted targets explicitly. Use atomic claims and a reconciliation test for a restart after commit and before the target queue is kicked.
- [ ] Extend `routed-task-queue.test.ts` and add a two-agent integration test based on `tests/cross-channel-recovery.integration.test.ts`. Cover authorization, note delivery without execution, FIFO ordering, duplicate submissions, concurrent unrelated work, one-hop limits, cancellation, and restart. Assert that child approvals and results go to the parent origin, that foreign owners receive nothing, and that the target's regular chat session stays intact.

## 4. Add private, searchable agent memory

Current continuity comes from the saved OpenCode session in `apps/agent-host/src/opencode-engine.ts`. Add explicit memories that can be retrieved even when a session starts fresh.

The memory tools are the interface, not a guarantee: the model can edit the store's SQLite file from its shell. This is acceptable for the agent's own private data, provided reads are defensive and nothing else trusts the contents.

- [ ] Add a memory store to the Agent Host under its existing task-state volume. Store a stable ID, title, bounded content, tags, source task ID, timestamps, and optional expiry. Scope every operation to that Host. Expose create, search, update, and delete tools with validated inputs. Apply size and count limits again on every read, for both tool results and the panel listing, so a row written outside the tools cannot inflate context or break a view. Skip malformed rows and rebuild an inconsistent search index; neither may fail the Host or a task. Keep writes explicit and avoid automatically copying full conversations or tool output.
  - Partial: `memory-store.ts` (node:sqlite, FTS5) and `memory-tools.ts` (create/search/update/delete, registered in `serve.ts`) are implemented with the limits re-applied on every read, malformed-row skipping, and index rebuild. No Server policy grants the `memory.*` operations to any task yet, so the tools are never exposed. Enabling them needs a product decision (default-on for chat tasks, or a per-agent opt-in).
- [x] Start with deterministic local keyword and tag retrieval using SQLite FTS5, which is available in the current Agent Host image (verified on Node 22.23.5 with `node:sqlite`). Keep a Docker test that creates an FTS5 table so an image change cannot remove it unnoticed. Rank by match and recency, limit the returned entries and total text, and treat retrieved contents as untrusted context. Avoid embedding services and cross-agent memory access in this phase.
- [x] Add authenticated per-agent memory inspection and deletion through the Server and Host, following the management pattern in `host-providers.ts`, `panel.ts`, and `apps/agent-host/src/http.ts`. Paginate the listing and enforce existing panel CSRF controls on mutations. Deletion removes the memory and its search entry. Document that prior chat transcripts and backups may still contain copies.
  - Host `GET /memories`, `POST /memories/:id/delete`; Server `host-memories.ts`; panel API with session and Origin checks and a **Review memory** page; documented in README and OPERATIONS.
- [ ] Test search ranking, input limits, expiry, deletion, restart with a fresh engine session, and isolation across agents. Include a fixture with instruction-like text in a memory and assert it cannot change tool grants or approval state. Include rows written directly to the database, both oversized and malformed, and assert bounded results and a working Host. Cover retained and explicitly purged Docker volumes using the existing lifecycle behavior.
  - Partial: store, tool, Host API, Server client and panel route tests cover ranking, limits, expiry, deletion, malformed/oversized rows, instruction-like text, hostile queries, and a store reopened after restart. Still pending: cross-agent isolation and volume-lifecycle tests, and the end-to-end check that a fresh engine session retrieves a note, which need the memory grant above.

## 5. Add shared tools and external MCP integrations

- [ ] Add an administrator-managed catalog in the Server SQLite database. A definition contains a stable ID, label, approved remote HTTPS endpoint, enabled tools and argument schemas, and an explicit read/write classification per tool. Store per-agent grants separately. Keep credentials scoped to each agent and integration, stored on the Server in a private directory following the `bot-secrets` pattern. They never enter an agent container. The panel can set, replace, or remove a secret without returning its value.
- [ ] Expose a catalog editor, per-agent grant controls, and a bounded connection test in the panel. Run discovery from the Server against an administrator-approved endpoint and display sanitized status and tool names. Discovery cannot execute tools. Treat remote tool metadata as untrusted and require the administrator to confirm the tools and schemas. Use the pinned OpenCode and MCP fixture from phase 1 to validate the integration path. [OpenCode MCP reference](https://opencode.ai/docs/mcp-servers/)
- [ ] Expose only granted catalog entries through the bundled MCP adapter, which forwards each call to the Server. The Server holds the MCP client for remote Streamable HTTP, with per-agent credentials, timeouts, response limits, and redirects disabled. Use a compatible maintained MCP client if the transport needs a library. A credential inside the container could be read by the model and used with `curl`, bypassing approvals and pinned schemas, so remote calls must not run there. The Server only connects to catalog endpoints and passes administrator-pinned tool arguments; it never runs agent-generated commands. Reject model-supplied endpoints. The Server enforces the granted tool ID, pinned schema, and classification before contacting the remote server. Because the Server now makes outbound requests to administrator-entered URLs, restrict catalog endpoints to HTTPS and document that the administrator is trusted to choose them.
- [ ] Treat unknown or changed tools as disabled until reviewed. Apply the advanced approval rules to mutating tools and recheck grant and schema immediately before execution. A remote server's read-only annotation alone cannot qualify a tool for a persistent allow rule. Cancel on turn termination where supported. Persist an invocation intent before a mutating call, record uncertain outcomes, and avoid replaying an uncertain write after a retry or restart.
- [ ] Verify with a local fixture configured only for tests. Grant one definition to two agents with independent credentials, revoke one grant, and show that only the remaining agent can call it. Cover disabled definitions, ungranted tools, schema changes, missing credentials, timeout, redirect rejection, denial before an upstream call, uncertain delivery, and secret redaction. Assert that no credential or upstream URL appears in any container file, environment variable, or tool payload. Use fixture recordings to assert call counts and the identity used for each connection.
